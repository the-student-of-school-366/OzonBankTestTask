# Посты и комментарии на GraphQL

Сервис хранит посты и дерево комментариев и отдаёт их через GraphQL. При запуске выбирается хранилище: PostgreSQL или память процесса. Комментарии вкладываются на любую глубину, списки читаются страницами, автор поста может закрыть обсуждение, а новые комментарии приходят подпиской.

## Структура

HTTP-запрос проходит через usecase и попадает в хранилище.

```
cmd/service                         сборка приложения и HTTP-сервер
cmd/migrate                         применение миграций
web                                 страница проверки
internal/domain                     пост, комментарий, страница, ошибки
internal/dto                        объекты запросов и ответов
internal/usecase/post               создание, чтение и настройка поста
internal/usecase/comment            создание комментария и публикация события
internal/usecase/subscription       подписка на комментарии поста
internal/broker                     контракт доставки событий
internal/repositories/memory        хранилище в памяти процесса
internal/repositories/postgres      PostgreSQL: схема, запросы, пул
internal/graphql                    схема, резолверы, пакетная загрузка, лимиты
internal/api                        HTTP-обработчик и Apollo Sandbox
internal/infrastructure/pubsub      хаб подписок одного процесса
internal/infrastructure/middleware  идентификатор запроса, автор, таймаут
internal/config                     YAML и переменные окружения
```

Оба хранилища реализуют одни и те же интерфейсы репозиториев. Страница проверки и Apollo Sandbox обращаются к `/graphql`.

## Технологии

### Внедрение зависимостей

Сборку приложения выполняет `uber/fx` в `cmd/service`. Контейнер создаёт хранилище, хаб подписок, сценарии постов, комментариев и подписки, затем GraphQL-обработчик и HTTP-сервер. Конструктор получает уже готовые зависимости и не вызывает чужие `New` вручную. При остановке объекты закрываются в обратном порядке: сначала GraphQL, затем хаб, затем пул базы.

### PostgreSQL

Доступ к базе идёт через пул `pgxpool`. Оба репозитория делят один пул на всё время работы сервиса. При подключении каждого физического соединения пул готовит именованные запросы. Текст запроса в соединение больше не передаётся: репозиторий вызывает его по имени и передаёт только параметры.

Сами запросы лежат в файлах `internal/repositories/postgres/queries/*.sql` и вшиты в бинарник. Пользовательские значения в SQL не подставляются.

Так закрывается SQL-инъекция. Заголовок, текст, автор и идентификаторы попадают только в параметры `$1`, `$2` и массивы `unnest`. Строка вроде `'; DROP TABLE posts; --` сохраняется как данные и не меняет команду. Имя выполняемого запроса выбирает код сервиса, а не клиент.

Запись комментария и смена разрешения на комментарии выполняются в транзакции `Read Committed`. Результат возвращается только после успешного `COMMIT`. Вставка держит пост блокировкой `FOR SHARE`, изменение флага — `FOR UPDATE`, поэтому эти операции не расходятся друг с другом. Схема накатывается миграциями Goose при старте сервиса.

### Образ приложения

Образ сервиса собирается в два этапа. Сначала `golang:1.27.4-alpine3.24` скачивает модули и собирает статически слинкованный бинарник: `CGO_ENABLED=0`, без служебных путей компилятора и без метаданных системы контроля версий. В итоговый образ `gcr.io/distroless/static-debian13:nonroot` копируются только этот бинарник и `config.yaml`. Компилятор, исходники и оболочка в него не попадают. Процесс работает от непривилегированного пользователя.

### Непрерывная проверка

При каждом push GitHub Actions поднимает PostgreSQL 17 и запускает `go vet ./...`, затем `go test -race ./...`. В задание передаётся `TEST_DATABASE_URL`, поэтому вместе с модульными тестами идут проверки базы. Описание workflow лежит в `.github/workflows/tests.yml`.

### Журнал

Записи пишет `log/slog`, уровень по умолчанию — `Info`. В журнале есть старт и остановка, выбранное хранилище, миграции, HTTP-запросы, события подписки и технические сбои хранилища. Откат транзакции, который не является обычным закрытием уже зафиксированной транзакции, тоже записывается. У запроса сохраняются метод, путь, статус, длительность и `request_id`. Внутренняя ошибка GraphQL пишется с тем же `request_id`, клиент получает общий текст. Тексты комментариев и строка подключения к базе в журнал не входят.

## Запуск

Нужны Docker и свободные порты `8082`, `8081` и `55432`.

```powershell
docker compose up --build -d --wait
```

| Адрес | Назначение |
| --- | --- |
| `http://localhost:8082` | Страница проверки |
| `http://localhost:8081/sandbox` | Apollo Sandbox |
| `http://localhost:8081/graphql` | GraphQL по HTTP |

Журнал приложения:

```powershell
docker compose logs -f app
```

`Ctrl+C` закрывает просмотр журналов, контейнеры продолжают работу. `docker compose down` останавливает контейнеры и сохраняет данные PostgreSQL.

Порты задаются переменными `WEB_PORT`, `APP_PORT` и `POSTGRES_PORT`. По умолчанию используется PostgreSQL. Учётные данные в репозитории демонстрационные: пользователь `ozon`, пароль `ozon_dev`.

Режим памяти поднимает только приложение, без PostgreSQL и страницы проверки. GraphQL доступен на порту `8081`.

```powershell
docker compose run --build --rm --no-deps --service-ports -e STORAGE=memory app
```

Тот же режим локально, с установленным Go:

```powershell
$env:STORAGE = 'memory'
go run ./cmd/service
```

Тесты PostgreSQL запускаются, если задан `TEST_DATABASE_URL`. Подготовка базы описана в [README сервиса](cmd/service/README.md).

## Проверка на странице

Откройте `http://localhost:8082`. Поле «Кто пишет» передаётся заголовком `X-User-ID`. Это демонстрационное имя. Пустое поле отправляет мутацию без автора.

1. От имени `alice` опубликуйте пост с открытыми комментариями и пост со снятым флажком.
2. Откройте первый пост. Добавьте несколько комментариев к посту и ответы кнопкой «Ответить». Кнопка «Ветка» открывает продолжение от выбранного комментария.
3. Укажите размер страницы `2` и нажмите «Обновить». Кнопки «Ещё посты», «Ещё комментарии» и «Ещё ответы» загружают следующую страницу.
4. Смените имя на `bob` и закройте комментарии чужого поста. Ожидается код `FORBIDDEN`. Верните `alice`, закройте обсуждение и отправьте комментарий. Ожидается код `COMMENTS_DISABLED`. Уже написанные комментарии остаются на месте.
5. Снова откройте комментарии, нажмите «Слушать этот пост» и напишите ещё один. Он появится в «Живой ленте». Комментарий к другому посту в эту ленту не попадает. «Остановить» прекращает доставку.

Остальные случаи, включая длину текста и чужого родителя, описаны в [инструкции страницы](web/README.md).

## Проверка через Apollo Sandbox

Откройте `http://localhost:8081/sandbox`. Для загрузки интерфейса нужен интернет.

Во вкладке **Headers** добавьте `X-User-ID` со значением `alice`. Для подписки в **Connection settings** укажите адрес `ws://localhost:8081/graphql` и реализацию **graphql-ws**.

Запросы и ожидаемые ответы собраны в [инструкции Apollo Sandbox](docs/apollo-sandbox-testing.md). Страница Sandbox отключается переменной `SANDBOX_ENABLED=false`.

## Почему выполнены требования задания

### Два хранилища

Usecase зависит от интерфейса репозитория. При `STORAGE=postgres` оба репозитория работают с одним пулом соединений. При `STORAGE=memory` один `memory.Store` обслуживает посты и комментарии. В памяти проверка поста, родителя и вставка комментария выполняются под той же блокировкой, что и смена разрешения на комментарии. В PostgreSQL эти действия проходят в одной транзакции.

### N+1

Резолверы `comments` и `replies` не обращаются к хранилищу по одному родителю. Загрузчик накапливает до 100 ключей. Ключ состоит из идентификатора родителя, размера страницы и курсора. Затем один раз вызывается `ListRootsBatch` или `ListRepliesBatch`.

В PostgreSQL это один prepared statement. Список запросов разворачивается через `unnest ... WITH ORDINALITY`, страница каждого родителя читается подзапросом `LATERAL`. Повтор одного поста с другим курсором остаётся отдельным элементом этого списка. Для корней и ответов заведены отдельные индексы под сортировку `(created_at DESC, id DESC)`. Чтение нескольких объектов по идентификатору выполняется одним условием `id = ANY($1)`.

Отдельный проход к базе нужен на каждый уровень вложенности запроса: посты, затем корни, затем ответы. Число родителей внутри уровня на число таких проходов не влияет. Хранилище в памяти предоставляет те же пакетные методы.

### Глубина ветки

Ответ хранится той же записью, что и корневой комментарий, и ссылается на своего родителя. Глубина хранимой ветки не ограничена. Один GraphQL-запрос ограничен глубиной и стоимостью, поэтому всё дерево целиком в нём не разворачивается. Следующий фрагмент читается запросом `comment(id)` и полем `replies`. На странице проверки для этого есть кнопка «Ветка».

### Пагинация

Посты, корневые комментарии и ответы сортируются по `(created_at DESC, id DESC)`. Курсор принадлежит одному списку. Для следующего запроса хранилище читает `first + 1` запись: лишняя запись выставляется в `hasNextPage`. Допустимый `first` — от 1 до 100.

### Запрет комментариев

Имя автора приходит в заголовке `X-User-ID` и не входит в поля GraphQL-мутации. Флаг `commentsEnabled` меняет только автор поста. Для остальных возвращается `FORBIDDEN`.

Вставка комментария и смена флага не должны разойтись. В PostgreSQL вставка читает пост с блокировкой `FOR SHARE`, а изменение флага берёт `FOR UPDATE`. Отключение дожидается уже начатых вставок. Вставка после отключения получает `COMMENTS_DISABLED`. В памяти обе операции проходят под одной блокировкой. Написанные комментарии после закрытия обсуждения по-прежнему читаются. Подписка на пост при этом сохраняется.

### Подписка

Поле `commentAdded` отдаёт новые корневые комментарии и ответы одного поста. Событие публикуется после успешной записи комментария. Доставка идёт через хаб текущего процесса. У каждой подписки ограниченная очередь. Подписчик, который не успевает читать, отключается, остальные продолжают получать события. Пропущенные события повторно не отправляются.
