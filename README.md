# Посты и комментарии на GraphQL

Сервис хранит посты и дерево комментариев и отдаёт их через GraphQL. Хранилище
выбирается при запуске: PostgreSQL или память процесса. Комментарии можно
вкладывать без ограничения глубины, списки читаются страницами, автор поста
может закрыть обсуждение, а новые комментарии приходят подпиской.

## Структура

Запрос проходит от HTTP к сценарию и только потом к хранилищу. GraphQL не
знает, PostgreSQL это или память.

```
cmd/service                         запуск HTTP-сервера и выбор хранилища
cmd/migrate                         отдельное применение миграций
web                                 страница ручной проверки
internal/domain                     пост, комментарий, страница, ошибки
internal/dto                        вход и выход API
internal/usecase/post               создание, чтение и настройка поста
internal/usecase/comment            комментарий и публикация события
internal/usecase/subscription       подписка на комментарии существующего поста
internal/broker                     контракт доставки: поток, ошибки, интерфейс
internal/repositories/memory        оба репозитория в одном процессе
internal/repositories/postgres      SQL, миграции и пул
internal/graphql                    схема, резолверы, загрузчики, лимиты запроса
internal/api                        HTTP-обработчик и Apollo Sandbox
internal/infrastructure/pubsub      хаб подписок внутри процесса
internal/infrastructure/middleware  идентификатор запроса, автор, таймаут
internal/config                     YAML и переменные окружения
```

Один и тот же сценарий получает либо `memory.Store`, либо пару репозиториев
PostgreSQL. Страница `web` и Sandbox ходят в один и тот же `/graphql`.

## Запуск

Нужны Docker и свободные порты `8082`, `8081` и `55432`.

```powershell
docker compose up --build -d --wait
docker compose ps
```

| Адрес | Что открыть |
| --- | --- |
| `http://localhost:8082` | Страница проверки |
| `http://localhost:8081/sandbox` | Apollo Sandbox |
| `http://localhost:8081/graphql` | GraphQL по HTTP |
| `ws://localhost:8081/graphql` | Подписки, протокол `graphql-transport-ws` |

Пока в журналах нет строки `service started`, миграции ещё идут:

```powershell
docker compose logs -f app
```

`Ctrl+C` закрывает только просмотр журналов. `docker compose down` останавливает
контейнеры и сохраняет данные PostgreSQL.

Порты меняются переменными `WEB_PORT`, `APP_PORT` и `POSTGRES_PORT`. Хранилище
по умолчанию — PostgreSQL. Память процесса:

```powershell
docker compose run --build --rm --no-deps --service-ports -e STORAGE=memory app
```

В этом режиме страница `web` не поднимается: контейнер приложения доступен на
порту `8081`. Локально, без Docker-образа приложения:

```powershell
$env:STORAGE = 'memory'
go run ./cmd/service
```

Учётные данные базы в репозитории демонстрационные (`ozon` / `ozon_dev`). Для
настоящих секретов их задают переменными окружения до первой инициализации тома.

Автоматические проверки:

```powershell
go test ./... -count=1
go vet ./...
```

Интеграционные тесты PostgreSQL пропускаются, пока не задан `TEST_DATABASE_URL`.
Как поднять отдельную тестовую базу, описано в
[README сервиса](cmd/service/README.md).

## Журнал

Сервис пишет журнал через `log/slog` в стандартный поток ошибок. Уровень по
умолчанию — `Info`. Смотреть его можно так:

```powershell
docker compose logs -f app
```

В журнал попадают старт и остановка, выбранное хранилище, применение миграций,
включение Sandbox, каждый HTTP-запрос и события подписки: начало, отказ из-за
лимита, отключение медленного подписчика и остановка хаба. У запроса пишутся
метод, путь, статус, длительность и `request_id`. Внутренняя ошибка GraphQL
дописывается с тем же `request_id`; клиент при этом видит только общий текст.

Текст комментариев, тело запроса и строка подключения к базе в журнал не
попадают. Отдельная команда миграций пишет результат тем же `slog`.

## Проверка через страницу

Откройте `http://localhost:8082`. Поле «Кто пишет» уходит в заголовок
`X-User-ID` и не подтверждает личность. Пустое поле отправляет мутацию без
автора.

1. От имени `alice` опубликуйте пост с открытыми комментариями и пост с
   выключенным флажком.
2. Откройте первый пост, добавьте несколько корней и ответы кнопкой «Ответить».
   «Ветка» продолжает чтение с выбранного комментария.
3. Поставьте размер страницы `2` и нажмите «Обновить»: «Ещё посты», «Ещё
   комментарии» и «Ещё ответы» берут следующую страницу.
4. Смените имя на `bob` и закройте комментарии чужого поста: код `FORBIDDEN`.
   Верните `alice`, закройте обсуждение и напишите комментарий: код
   `COMMENTS_DISABLED`. Уже написанное остаётся на экране.
5. Снова откройте комментарии, нажмите «Слушать этот пост» и напишите ещё один
   комментарий. Он появится в «Живой ленте». Комментарий к другому посту в эту
   ленту не попадает. «Остановить» прекращает доставку.

Полный порядок, включая длину текста и чужого родителя, лежит в
[инструкции страницы](web/README.md).

## Проверка через Apollo Sandbox

Откройте `http://localhost:8081/sandbox`. Для загрузки интерфейса нужен
интернет. Адрес запросов — `http://localhost:8081/graphql`.

Во вкладке **Headers** добавьте `X-User-ID: alice`. Для подписки в
**Connection settings** укажите `ws://localhost:8081/graphql` и реализацию
**graphql-ws** (подпротокол `graphql-transport-ws`). На серверный `ping`
клиент отвечает `pong`.

Тот же набор сценариев запросами и ожидаемыми ответами описан в
[инструкции Apollo Sandbox](docs/apollo-sandbox-testing.md). Sandbox выключается
переменной `SANDBOX_ENABLED=false`.

## Как закрыты требования задания

### Два хранилища

Сценарии зависят от интерфейсов репозитория, а не от PostgreSQL. `cmd/service`
по значению `STORAGE` собирает либо один `memory.Store` на оба сценария, либо
репозитории поверх общего пула. Память защищена одним `RWMutex`: проверка поста,
родителя и вставка комментария не расходятся с переключением разрешения.
PostgreSQL делает то же в транзакции.

### N+1

Список постов с комментариями и ответами не порождает запрос на каждого
родителя. Резолверы `comments` и `replies` отдают загрузчику ключ из
идентификатора, размера страницы и курсора. Загрузчик собирает до 100 ключей и
один раз вызывает `ListRootsBatch` или `ListRepliesBatch`.

В PostgreSQL это один prepared statement: массив запросов разворачивается через
`unnest ... WITH ORDINALITY`, а страница каждого родителя читается подзапросом
`LATERAL` с `LIMIT`. Разные курсоры одного поста остаются разными элементами
массива. Частичные индексы совпадают с сортировкой `(created_at DESC, id DESC)`
отдельно для корней и для ответов. Чтение по идентификаторам идёт одним
`WHERE id = ANY($1)`.

Глубина запроса по-прежнему даёт отдельный проход на уровень: посты, затем все
корни, затем все ответы. Число родителей на уровне число запросов не умножает.
Память предоставляет те же пакетные методы. Тест репозитория проверяет, что
пакет из нескольких страниц увеличивает счётчик prepared statement на единицу.

### Вложенность и предел одного запроса

Ветка хранится без ограничения глубины: ответ — такая же запись со своим
родителем. Один GraphQL-запрос при этом ограничен глубиной и стоимостью, чтобы
клиент не разворачивал всё дерево сразу. Продолжение начинается с
`comment(id)` и снова запрашивает `replies`. На странице это кнопка «Ветка».

### Пагинация

Списки постов, корней и ответов идут по ключу `(created_at DESC, id DESC)`.
Курсор кодирует позицию и привязан к конкретному списку: его нельзя перенести
на другой пост, другого родителя или другой вид списка. Страница запрашивает
`first + 1` запись, лишняя показывает `hasNextPage`. Допустимый `first` — от 1
до 100.

### Запрет комментариев

Автор передаётся заголовком и не входит в GraphQL-ввод. Менять
`commentsEnabled` может только автор поста, иначе возвращается `FORBIDDEN`.

Закрытие не должно пропустить комментарий, который уже проверяет разрешение.
В PostgreSQL вставка читает пост с `FOR SHARE`, а смена флага берёт
`FOR UPDATE`: новое отключение ждёт начатые вставки, а вставка после
отключения получает `COMMENTS_DISABLED`. В памяти обе операции идут под одной
блокировкой. Существующие комментарии после закрытия по-прежнему читаются.
Подписка от запрета не зависит.

### Подписка

`commentAdded` — публичная подписка на новые корни и ответы одного поста.
Событие публикует сценарий создания комментария после успешной записи.
Доставка идёт через хаб внутри процесса: у каждой подписки ограниченная
очередь, медленный подписчик отключается и не держит остальных. Истории и
повтора пропущенных событий нет. Контракт потока лежит в `internal/broker`,
поэтому хаб не зависит от сценария.
